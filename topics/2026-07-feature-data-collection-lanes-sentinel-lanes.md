## System manifest sentinel lane (2026-09-06)

State as of 2026-09-06, all UNCOMMITTED in the live tree. Source memory description: "Manifest regeneration mechanics, the :966 dedup fix (3 stores, not 2), the measured D-015 cost baseline, and the self-falsifying audit sentinels". Also feeds Melange architecture and system of record; actor detail on [[sentinel-collectors]].

- **The `:966` dedup defect is FIXED.** `fec/audit/build_system_manifest.py:966` appended `newest_file` with no membership test against `top`; because `pick_sentinels` truncates `by_size` to `SENTINEL_COUNT` at `:1073` BEFORE the `seen` dedup at `:1090`, a file that was both largest and newest ate a slot and evicted the true third-largest. The fix adds `and newest_file[0] not in {t[0] for t in top}` (rows are `(rel, size, mtime)`).
- Blast radius was **3 stores, not the 2 the brain listed:** `mdata.bicam_zips` 2 to 3, `mdata.bicam_extracted` 2 to 3, `repo.data_district` 2 to 3. **`mdata.residual` was NOT affected** - it has 4 rows; that entry in the old note is stale. The worktree copy of the producer still carries the defect.
- **Regenerating is riskier than it looks.** `dump_atomic` overwrites `data/system/system_manifest.json` unconditionally - NO backup, no hash gate - and the prior manifest is uncommitted, so it is the only copy. Copy it aside first. (The "manifests in backups/, hash-gated" memory belongs to the sentinel-workbook lane, a different apparatus - see the previous section.) Invoke the LIVE tree's script by absolute path: `paths.py` is imported from the script's own tree (`:81-82`), so `MONEYBALL_ROOT` fixes `ROOT` but not which code runs, and the worktree's producer is a different file.
- **D-015 cost baseline, measured for the first time: ~147-167 s** (146.8 s / 166.9 s, 13.7% variance). The brain's uncaptured "~29 min" is not borne out on a warm cache. Scope if the cap is lifted: 71 sentinel rows across 25 stores / 79.46 GiB currently skipped, vs 81.37 MiB hashed - a ~1000x increase. `repo.git` has 3 sentinels, 0 hashed, all `git gc`-retirable.
- **Live-regen then live-audit is NOT the DE-012 vacuous pass.** `system_manifest_check.py:8-13` refuses any manifest that does not predate the checking process and asserts the producer is absent from `sys.modules`. But 582/0 straight after a regen is over-fit by construction - A2/A2b cannot fail when the manifest is 78 s old. The meaningful test is the next chain-terminal audit.
- **The 8 `A2b … sentinels unchanged` failures return on every chain run.** Regeneration clears the instance, never the cause (DE-011). They are pattern-tolerated by `audit_failure_gate.py:69-72`, so they do not block publish. Real remedy is excluding chain outputs from sentinel duty.
- **Unruled risk:** `audit_full` writes its own pinned sentinels - `_audit_tmp_optimize.json` (`:161-162`) and `_audit_tmp_frontier.json` (`:197-198`) - ~2,300 lines before checking them at `:2473`. If either output ever varies, `repo.data_lobbying` and `repo.data_money` fail on every run after the first and **regeneration cannot fix it**.
- **Why:** this lane's failure modes all look like data corruption and are not. Reading a red A2b as a regression, or regenerating to "fix" it, wastes a gate and hides the real defect.
