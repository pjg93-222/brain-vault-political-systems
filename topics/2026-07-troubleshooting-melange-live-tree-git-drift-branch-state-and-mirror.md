### 2026-08-14 (later, CPU-pegged incident): worktrees now live OUTSIDE OneDrive at `C:\melange-worktrees\<name>`

- Ten registered worktrees were relocated with `git worktree move` (same volume, instant metadata rename, not a copy; git rewrites its admin pointers). Verified: 0 broken, all branches intact, all 21 uncommitted tracked edits preserved. `git worktree list --porcelain` is now the ONLY way to find a worktree - do not assume `.claude/worktrees`.
- Root cause of the pathology: `audits/legfix5` is GIT-TRACKED (38,893 files, ~18 GB), so every `worktree add` materialises ~18 GB inside the OneDrive sync root, and OneDrive + Defender + Carbonite + LG "gram chat" GSearch (5 procs) all crawl every copy - CPU sat at 97.7% of 8 cores (OneDrive alone 2.9 cores); relocation took it to ~35%.
- `git worktree move` fails two distinct ways here and NEITHER is corruption: "Permission denied" = a live session/OneDrive handle (retry after it settles), "Function not implemented" (ENOSYS) = OneDrive's cloud filter refusing the rename. Deletion was REJECTED as the fix - 9 trees held uncommitted source edits and 6 more held untracked design docs/.candidate artifacts; move, don't delete.
- Junction probe (for redirecting FUTURE worktrees): OneDrive tags dirs it manages `0x9000e01a` (cloud), a junction stays `0xa0000003` (mount point) and was NOT adopted after 50 s of active scanning, so junctioning `.claude/worktrees` to an out-of-OneDrive target is the likely permanent fix, but it needs that dir EMPTY first. SAFETY: never remove a junction with PowerShell `Remove-Item -Recurse` - it can delete the TARGET's contents; use `cmd /c rmdir <link>` or `[System.IO.Directory]::Delete($p,$false)`.
- The "OneDrive holds the directory handle" folklore for the 4 empty deregistered shells is FALSE - disproven by experiment: OneDrive was killed outright (0 processes running) and all four deletions STILL failed with "used by another process"; `attrib -R` did not help (its recursion just churns OneDrive). The real holders are idle `powershell.exe` processes whose CWD is pinned inside the shell dirs (a CWD handle, not a file handle). Find them with psutil (installed, 7.2.2): `for p in psutil.process_iter(): p.cwd()` and match the dir name - 5 holders were found for 4 dirs (4 parented to a live `claude.exe`, 1 fully orphaned), all idle (< 0.02 CPU-sec/10 s, no child commands), 8.9-48 h old. Same mechanism as "a session cannot delete its own worktree", but the pin outlives the worktree by days.
- Do NOT restart OneDrive to fix this: it does not release the pin, and the restart triggers a full sync-root re-scan PLUS a Windows Search re-index (searchindexer + searchhost + searchprotocolhost ~84%), taking CPU from 35% back to ~67% and RISING for many minutes. Reboot, or kill the pinned shells. Also noted: this box registers two AV engines (Windows Defender + McAfee), and `mc-sustainability` was separately seen at 91.7%.

Check mtimes (`find fec -maxdepth 1 -name '*.py' -mmin -30`) before staging. Corollary: a session cannot delete its own worktree - `git worktree remove` deregisters it but the directory delete fails Permission-denied while the harness keeps cwd inside it; `worktree prune` also can't clear ~24 other stale registrations (OneDrive locks), which is why the worktree list keeps growing.
- CORRECTION to the DATA claim in the 2026-07-14 entry: data isolation depends on `MONEYBALL_ROOT`. On 2026-07-15 it is UNSET (process/User/Machine all empty), so `paths.py` ROOT = the worktree the script runs from - each worktree reads/writes its OWN data, and a fresh worktree has NO gitignored data artifacts (proved: kernel tests from a worktree hit `FileNotFoundError` on that worktree's `congestion.json`, not the live one).
