## Integrated 17-topic x 3-role scraper (Moneyball Legislative Score - Raw)

### CURRENT design (2026-06-22, latest): lives in `congress_member_scraper.R`

The user's word was "swapped", and `original-cosponsor` is confirmed against `congress_member_scraper_examination_query_backup.R`. **`field=cosponsor` live behavior still UNVERIFIED** (offline-clean only).
- **Decay = `DECAY_PER_CONGRESS=0.8`**, applied to the 3 COUNT columns ONLY (sponsor/orig-cos/cosponsor); averages + success rates stay un-decayed (user's explicit call this session, 2026-06-22 - supersedes the old 0.5/all-counts note).
- Extraction (`parse_result_node`/`parse_single_bill_page`/`extract_bill_summary`) is UNCHANGED; the cookie-replay/rounds/browser-fallback machinery is intact plus two fixes:

### Stability guard (2026-06-23)
Added after a flaky-server resume baked bad data: `MAX_CHALLENGED_BEFORE_ABORT=40` in `scrape_members_for_template` - if >40 members are still challenged AFTER the HTTP rounds + re-harvest, `stop()` the run WITHOUT saving the pass (instead of limping through the per-member browser fallback, which silently records challenged members as "0 bills" and then marks the pass done). Why it mattered: a resume during congress.gov instability saved tcpa orig/cosponsor passes with implausible counts (13 and 7 rows when cosponsor is normally the largest); those 2 passes were removed (backup `congress_scrape_checkpoint.rds.bak_20260623_131614`) and redo cleanly. Healthy steady state leaves only a handful challenged, so the guard never fires then.

### Stage 3 - cosponsor SNA edges (2026-06-23, appended at END of `congress_member_scraper.R`)
- For each SPONSORED bill (Role=="sponsor" rows already scraped; scope = our 17-topic bills, NOT all bills), fetch its cosponsors page and build a **DIRECTED sponsor -> cosponsor weighted graph**: original cosponsor (trailing `*`) = 1.0, regular = 0.5, summed across the sponsor's bills = edge weight ("closeness").
- Nodes keyed by **bioguide** (sponsor bioguide via `get_member_bioguide()` from the roster CSV; cosponsor bioguide parsed `[A-Z][0-9]{6}` from the `/member/` href) so a member who both sponsors and cosponsors is ONE node.
- Cosponsors page URL = DetailLink+`/cosponsors` (== the `li:nth-child(6) a` tab); cosponsors read from `#main a` filtered to `/member/` links; the `*` is read from the surrounding cell (`xml2::xml_parent`) since it sits outside the `<a>`.
- igraph metrics: weighted in/out strength, in/out degree, closeness+betweenness (weights=1/Weight so stronger tie = closer), eigenvector, pagerank (weights=Weight). Output `congress_cosponsor_network_<ts>.xlsx` (Edges + Centrality).
- **Gated `RUN_COSPONSOR_EDGES<-FALSE`** (default OFF) + resumable via `congress_cosponsor_checkpoint.rds`; igraph was installed this session. Logic offline-tested (parse, agg, igraph, node reconciliation). User envisions a full SNA graph later ("not there yet").

### Stage decoupling + guardrails (2026-06-24)
After a re-scrape silently undercounted MBL sponsor 90 -> 65 during a flaky cookie window. The 3 stages are separable in the checkpoint: STAGE 1 = `$passes` (51) + `$scrape_complete` flag; STAGE 2 = `$summaries_done`/`$bills`; STAGE 3 = the separate `congress_cosponsor_checkpoint.rds`. To re-do summaries/cosponsor WITHOUT re-scraping: clear summaries_done/bills (Stage 2) and/or delete the cosponsor rds (Stage 3); Stage 1 stays put.
- **GUARDRAIL 1 (lock):** when `scrape_complete=TRUE`, Stage 1 reuses cached passes verbatim and NEVER re-scrapes; if any of the 51 `ROLE_KEYS` pass is missing it STOPS with instructions (restore backup, or set `scrape_complete<-FALSE` to deliberately re-scrape) instead of silently re-scraping part of a finished scrape. The flag auto-sets TRUE when all 51 passes exist.
- **GUARDRAIL 2 (no-regression):** `scrape_members_for_template` now returns `n_fallback` (members that fell to the unreliable browser fallback); a (re)scrape that is SMALLER than the cached pass AND used fallback does NOT overwrite - the larger trusted version is kept.
- Both offline-tested. Current state (2026-06-24): Stage 1 LOCKED complete (51 passes), Stages 2+3 checkpoints wiped (will re-do cleanly with the retry/backoff). Checkpoint backups `congress_scrape_checkpoint.rds.bak_*` kept.

### PRIOR approach A: PIVOT to the simple looped scraper (2026-06-22, SUPERSEDED the same day)
User wanted the SIMPLE version -> `congress_scraper_looped.R`. They rejected the role logic (field-swap / `/cosponsors` page-fetch) as overcomplicated. The role distinction was to be just MORE LINKS in `congress_search_urls.R`: sponsor / original-cosponsor / cosponsor each their own verbatim URL (congress.gov generates structurally different raw-JSON per role - NOT a token swap), added as separate `*_url_parts` vectors. `congress_scraper_looped.R` auto-detects EVERY `*_url_parts` vector in file order, runs the proven per-member scrape on each link, then moves to the next ("just go down the list"). Output = one Results sheet, member rows in sheet order, 3 cols per link (Count / AvgCosp / Success%) labeled by link name (17 links -> 51 cols). Default `DECAY_PER_CONGRESS=1.0` (raw integer counts, matching the original/sheet). Kept the proven machinery + all fixes (cookie-replay, rounds, `TARGET_RPS=5` pacing, NA/429 guards, progress, per-link checkpoint/resume). The big `congress_moneyball_integrated.R` below is the prior (superseded) approach.

### PRIOR approach B: `congress_moneyball_integrated.R` (built 2026-06-21, Draft Systems folder)
Merges the per-member scraper with the 17 advanced-search templates in `congress_search_urls.R`, scraping all topics for the whole roster in one session.
- **Architecture is PER-MEMBER, not per-topic.** The assistant initially proposed per-topic (drop `__MEMBER__`, group by sponsor) to cut requests; the user rejected it - keep the member as the switch.
- **Throttle model:** 17 topics run in 8 BATCHES (`TOPIC_BATCHES`, "rounds" = groups of topics) with `BATCH_PAUSE` between; `MAX_RETRIES` retries challenged members WITHIN a topic (re-harvest + `RETRY_BACKOFF`). congress.gov threw "technical difficulties" repeatedly at 5 workers (searches fired full-speed - only paging/cosponsors were paused), so **interval pacing to `TARGET_RPS`** (each worker sleeps the remainder of its `HTTP_WORKERS/TARGET_RPS` slot per member -> aggregate is a CAP not a floor; to actually HIT the target you need `HTTP_WORKERS ≥ TARGET_RPS × fetch-secs`). Now **`HTTP_WORKERS=6`, `TARGET_RPS=5`** - 8/s got 429/503-rate-limited on ~65% of requests, so congress.gov caps ~5/s sustained. **Adaptive `SITE_COOLDOWN`** (180s when >40% of a try fails), **429/503 Retry-After honoring** in `fetch_html_http`.
- **BUG FIXED (mass "missing value where TRUE/FALSE needed"):** a 503 with no Retry-After made `ra <- as.numeric(NULL) = numeric(0)`, and `if (!is.na(ra) && ra > 0)` errors on zero-length in R 4.6 -> every rate-limited member "failed" and triggered the cooldown. Fix: `length(ra)==1 &&` guard, plus body-NA/empty guard + raw-bytes recovery + `isTRUE()` around the grepl checks in `fetch_html_http`/`fetch_rendered_html`. `MAX_RETRIES=5`, `RETRY_BACKOFF=30` cap 240, `BATCH_PAUSE` 45-90s. To dial: change `TARGET_RPS` (main knob) + keep `HTTP_WORKERS` >= it.
- **Why it felt slow vs the original single-topic scraper:** ~34x the volume (17 topics x sponsor+cosponsor passes), the `TARGET_RPS` cap, AND the original-split `/cosponsors` phase RAN SEQUENTIALLY in the main process - now PARALLELIZED (`fetch_cosponsors_df`/`parse_cosponsors_page` over DISTINCT bills via `future_lapply`, deduped, then attributed to members; replaced the old cached `fetch_cosponsors_page`/`original_cosponsored_bills`). Checkpointed/resumable. Param history: 5w/4r -> 10r/2w -> 5w/8batches -> 2w worker-pause -> 4w@4rps -> 8w@8rps + parallel cosponsors.
- **Maps to "Legislative Score - Raw"** (Excel Table `Table1`, 533 members rows 3-535, names col A): 8 columns per topic, topic *t* starts at sheet col `C + 8*(t-1)`; the 17 templates are in the sheet's exact topic order. Offsets: +0 Sponsor count, +1 Sponsor avg cosponsors, +2 Orig co-sponsor count, +3 Orig co avg, +4 co-sponsorship count, +5 Success Rate, +6 Sponsor success %, +7 Orig co-sponsor success %. +5 is normally an Excel formula `=mean(+6,+7)`; the script writes the equivalent VALUE.
- **Decay** by session of congress (more logical than year), `DECAY_PER_CONGRESS=0.5` (119=1, 118=.5, 117=.25), applied to COUNT columns only; set 1.0 to disable (superseded by 0.8 on 3 counts, see above). **Why:** older bills should weigh less; congress is already on every bill.
- **Roles: ALL THREE ON, original co-sponsor IMPERATIVE** (`SCRAPE_SPONSOR`, `SCRAPE_COSPONSOR` +4, `SPLIT_ORIGINAL_COSPONSOR` +2/+3/+7 incl. success rates). User: original co-sponsor + success rates are required. congress.gov `field=cosponsor` raw behavior and `/cosponsors` markup were UNVERIFIED live (the field-swap `%22field%22%3A%22sponsor%22` -> `cosponsor` is offline-verified clean). `fetch_cosponsors_page` detects originals by the "*" marker, else falls back to earliest cosponsor-date (= intro date); run WARNS if 0 originals found run-wide. **Must confirm with `validate_original("<bill detail link>")` against the live site and tune the parser to the real markup.** Failed fetches preserve existing values (FailedFetches sheet); `is_site_error_html` stops the congress.gov "technical difficulties" page (can arrive 200) being recorded as a false 0.
- **Resilience (added after a stalled/"crashed" run):** worker `message()`s never reach the console, so the parallel scrape looked frozen -> progress is now `progressr` `with_progress`+`progressor` bars driven from the main process (`handlers("txtprogressbar")`), one per topic/role and one for the original-split. The `future_lapply` is wrapped in `tryCatch` so a parallel/infra error is printed (named) and treated as all-challenged (retried) instead of crashing or silently zeroing. Per-topic **checkpoint/resume**: `RESUME=TRUE` saves `moneyball_progress.rds` after each topic and resumes finished topics on restart (deleted on clean finish). The suspected `is.na(xml_node)` crash was a red herring - it does not error in R 4.6.0/rvest here (switched to `inherits(a,"xml_missing")` anyway); the original stall was just invisible progress + manual interrupt. **Chromote 0.5.1 "timed out waiting for response to command Page.navigate"** fixed: `session$Page$navigate(url, wait_ = FALSE)` (async - our polling detects readiness) + `session$default_timeout <- CHROMOTE_TIMEOUT` (120s) in both `harvest_cf_session` and `fetch_rendered_html`; harvest is now crash-proof (tryCatch around session-create + navigate, returns NULL on failure instead of killing the run).
- **Roster / territories / accents:** roster = the sheet's 533 names (`legscore_current_raw.csv`). Verified 2026-06-22 against theunitedstates.io: all **531 voting members present, 0 missing**, plus 2 territory delegates **Eleanor Norton (DC) + Pablo Hernández Rivera (PR) - user wants these KEPT**; the other 4 territories (AS/GU/MP/VI) are intentionally absent. Accents already round-trip correctly (CSV read, `build_url` -> `Pablo+Hern%C3%A1ndez+Rivera`, writexl output); added `ACCENT_ASCII_FALLBACK` (retry a 0-hit accented search once as ASCII via iconv, in case congress.gov indexed without diacritics).
- **Safe paste-back:** reads current sheet values from `legscore_current_raw.csv` (Python snapshot via openpyxl on a temp copy, since the live xlsx is usually locked open in Excel) as the base matrix, overwrites only computed columns, so un-scraped columns keep their values. Output `moneyball_legscore_<ts>.xlsx`, sheet `LegScore_Raw_PASTE` - paste C3:EH535. Also `Bills`, `ZeroHitMembers` (name-mismatch candidates -> `MEMBER_NAME_OVERRIDES`), `RunConfig`.
