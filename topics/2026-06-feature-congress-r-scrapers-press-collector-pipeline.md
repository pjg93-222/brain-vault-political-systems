# Press text collector and one-command pipeline (Congress R scrapers)

> The press text collector and one-command pipeline of 2026-06-18/19: anti-stall hardening, the fast analyzer, the combined driver, throughput tuning, the collector crash fix, the chromote 403 lane and coverage bugs, and the validity verdict. Part of [[2026-06-feature-congress-r-scrapers]] (project [[melange-systems]]).

## Press scraper: fallback chain, third-party sources and coverage work

### Text-collection anti-stall hardening (2026-06-18)
Stage 4 full-text used to "silently stall": the sequential JS-member block (`res_js <- lapply(seq_bgs,...)` in `stage_fulltext`, main process, workers idle) emitted NO progress and `fetch_html_js` ran synchronous chromote CDP calls (`Page$navigate`/`Runtime$evaluate`) with NO wall-clock cap, so one wedged headless tab blocked forever; `FULLTEXT_MODE="all"` made every release walk static -> chromote -> Wayback (60-90s) serially, and the per-member checkpoint saved only at the END (a mid-member stall lost all its work). Fixes (no new deps; fetch semantics unchanged):
1. HARD per-call cap `JS_NAV_TIMEOUT<-25` via base-R `setTimeLimit(elapsed=,transient=TRUE)` wrapped around the CDP block in `fetch_html_js` - overrun throws, the existing `error -> "JS_SESSION_DEAD"` handler kills+respawns the session and skips the URL (validated: setTimeLimit aborts a blocked Sys.sleep at the cap and is catchable); plus `options(chromote.timeout=JS_NAV_TIMEOUT)`.
2. `fetch_member_fulltext` lapply -> `for` with per-member wall-clock budget `JS_MEMBER_BUDGET<-600`s (js only; parallel members httr-bounded, budget=Inf) - on overrun save partial + `break`, resumes next run via `done<-setdiff(urls,done)`.
3. Incremental checkpoint every `CKPT_EVERY<-25` urls (`flush_ck`) so a stop/stall never discards completed fetches.
4. Per-member heartbeat in the seq JS block (`JS [k/n] bg: N urls -> M bodies (Ns)` + `flush.console`) - kills the "silent".
NOT done (optional next lever): parallelizing JS members across a chromote-session pool (deliberately kept sequential - chromote-in-future-workers is unsafe). Net: worst case is now bounded (sum of js members x 600s, resumable) instead of an unbounded silent hang. (Later superseded for the collector: `setTimeLimit` replaced by chromote's own `default_timeout`, 2026-06-19, see below.)

### Fast analyzer `cu_text_collector.R` (2026-06-18)
- The `future`/synchronous Stage-4 fetch in the main scraper never finished (>10h, partial coverage) - root cause MEASURED: not network but **parse**. `read_html`+`extract_release` = **~62ms/page = ~16 pages/s on ONE core**; a single process is parse-bound (~4.7h for 273k). Network (libcurl multi, HTTP/2 multiplexed) is ~12.7 url/s per host but many hosts run in parallel, so it is not the cap.
- Solution = a separate drop-in collector that **parallelizes parse across cores by sharding members across N worker PROCESSES** (each owns distinct hosts -> per-host politeness automatic), each worker running an **async curl multi pool** (`TOTAL_CON` 24, `HOST_CON` 6, multiplex) so fetch overlaps parse. It REUSES the scraper's `extract_release` (sources it with `CU_PR_NO_AUTORUN=1`) and writes the SAME `pr_checkpoints/fulltext/<bg>.rds` (url,title_detail,date_detail,body) the scorer reads - so scoring/Stage5+ unchanged.
- Default role = orchestrator: `Rscript cu_text_collector.R` auto-launches `CU_TC_PROCS` (default 6) worker subprocesses (`Rscript cu_text_collector.R <i> <n>`, logs to `collector_shard_i.log`), prints ONE aggregate heartbeat (bodies cached / url-s / ETA / shards-done by polling fulltext + logs), then writes `collector_residual.csv` (members still missing bodies -> feed to the main scraper's chromote/Wayback lane). Resumable (skips urls with body+date), incrementally checkpointed (flush every `CU_TC_FLUSH=8000`), no chromote in hot path -> cannot hang.
- **Measured ceilings: 6 cores ~ 47min, 8 ~ 36min** (vs >10h). Knobs: `CU_TC_PROCS`/`TOTAL_CON`/`HOST_CON`/`CHUNK`(1500)/`FLUSH`/`LIMIT`(dry-run)/`CU_CKPT_DIR`(alt store)/`CU_TC_SHARD`("i/n"). Integration-tested end-to-end on a temp store (orchestrator + 2 workers + limit). Validated parse fix: top-level multiline `if/else` in an R assignment is a parse error - keep `x<-if(c)a else b` on one line or use a separate `if`.
- Workflow: (1) `Rscript cu_text_collector.R` (~47min, fills ~all bodies), (2) check `collector_residual.csv`, (3) `Rscript cu_press_release_scraper.R` (residual JS/Wayback + score) or `CU_PR_OFFLINE=1 ...` to score cache only. RAM: ~450MB/worker -> 6 procs ~3GB (safe with ~6.9GB free); set `CU_TC_PROCS=8` if RAM freed.
- **Optimization round (2026-06-18):** parse re-measured at ~30ms/page on typical pages (62ms was the one giant member's heavier pages) -> real run ~30min @6 cores. Stripping `<script>/<style>/<svg>` before `read_html` measured ZERO speedup (cost is core libxml2 parse, not inline JS) - ruled out, do not retry it. Six wins applied and integration-tested: (1) **shards balanced by URL count** (greedy: heaviest member -> lightest shard, via orchestrator-written `collector_plan.rds`) instead of name-hash, so no shard becomes the tail; (2) **one persistent curl pool per worker** (was per-chunk) -> HTTP/2 keepalive survives across chunks (later changed, see 2026-06-19 crash fix); (3) **retry only transient** (libcurl `fail` + HTTP 5xx); 4xx and empty-200 (JS-only) are permanent `miss`, no wasted second pass - big win on Wayback/dead-URL members; (4) orchestrator builds ONE plan (single index+cache scan) and workers read their slice -> no 6x redundant full scans, lighter workers; (5) heartbeat reads cheap cumulative "ok N" from shard logs (not re-reading all fulltext rds every 30s) + **stall guard** (break if no progress 10min -> survives a crashed worker); (6) `TOTAL_CON` 24 -> 40 (Little's law: ~0.8s latency x ~40/s core needs ~32 in-flight to not starve parse). Plan auto-unlinked at end.

### Combined one-command driver `run_cu_pipeline.R` (2026-06-18)
Runs the WHOLE analysis end-to-end: `[1/2] cu_text_collector.R` (fast async body fill) then `[2/2] cu_press_release_scraper.R` (bodies now cached -> only residual JS/Wayback members + committee/third-party-news/cosponsor stages + Stage-5 scoring -> writes `cu_press_releases_scored.{csv,xlsx}`, `cu_press_releases_category_scores.csv`, `cu_net_scores_by_category.xlsx`, `all_press_release_index.csv`). Each step is a `system2(wait=TRUE)` subprocess streaming to console; env inherits 3 levels deep (pipeline -> collector -> workers, verified). Knobs: `CU_TC_PROCS` passes through; `CU_PIPE_SKIP_COLLECT=1` (re-score from cache), `CU_PIPE_COLLECT_ONLY=1` (stop after collect), `CU_PR_OFFLINE=1` (step-2 scores from cache, no network -> skips news+cosponsor). The collector itself stays collect-only; the pipeline is the combined entry. End-to-end ~30min collect + ~10-30min score. Both stages resumable so a re-run continues. (Later, 2026-06-21, Stage 5 `run_stage5.R` became step [3/3]: see the stance section in [[2026-06-feature-congress-r-scrapers-stage5-debate-lsd]].)

### Throughput tuning (2026-06-18)
The `"all"` body sweep = **286,335 indexed releases** (mean 533/member, max 6,366, 64 members >1,000; only ~13.5k bodies were cached -> ~273k remained). Measured **~0.96s/article** (cold cross-host; real run amortizes via per-host keepalive). Old 8-worker/0.5s-delay projection ~ **12.4h**. Two safe levers (no coverage change, per-host rate still <2 req/s since each member is walked by ONE worker): (1) `FUTURE_WORKERS` now env-configurable via `CU_PR_WORKERS` (default 24 ~ 6GB, user-confirmed for this box; 8-core/31.5GB -> 32 fine with other apps closed, 16 to share; work is ~90% network-wait so oversubscribing cores is correct, RAM ~250MB/worker is the limit); (2) new `FULLTEXT_DELAY` (env `CU_PR_FT_DELAY`, default 0.15s) for the bulk live-site body fetch via a new `delay=` arg on `fetch_html` - **Wayback/discovery/index stay on `POLITE_DELAY=0.5`** (archive.org throttles). Projections @0.96s: 16w ~ 4.5h, 24w ~ 3.0h, 32w ~ 2.3h. Resumable (per-member + every-25-url checkpoints) so an interrupted run continues. Pole = biggest member 6,366 x 0.96 ~ 1.7h on one worker, still under the aggregate at <=32 workers, so member-sharding (higher per-host concurrency -> block risk) is deliberately NOT done.

### Fast pipeline = collector + scraper; collector crash fixed (2026-06-19)
The efficient ("fable") design is `run_cu_pipeline.R` (ONE command): step 1 `cu_text_collector.R` = async multi-core libcurl-multi/HTTP2 body collector (shards members across `CU_TC_PROCS=6` worker procs, balanced by URL count, reuses `extract_release`+`CHECKPOINT_DIR` from the scraper via `CU_PR_NO_AUTORUN=1`, writes the same `pr_checkpoints/fulltext/<bg>.rds`, ~70-80 url/s/shard); step 2 `cu_press_release_scraper.R` run with `CU_PR_SKIP_FETCH=1` + `CU_PR_NO_CHROMOTE=1` + `CU_PR_WORKERS=4` so it scores from the collector cache (NO slow synchronous re-fetch) and runs the news/cosponsor stages.
- **Running the monolith `cu_press_release_scraper.R` DIRECTLY with `FULLTEXT_MODE="all"` is the 10h trap (serial per-member httr) - do not; use the pipeline.**
- BUG FOUND+FIXED: every collector shard hard-crashed (no catchable R error, just "Execution halted") right after its "3000/5998" heartbeat - a single persistent libcurl pool accumulates HTTP/2 connection state and crashes the process past ~3-4k transfers on Windows. Fix in `run_all`: fresh `new_pool()` PER CHUNK (<=`CHUNK=1500` transfers/pool, measured safe >3300) + `rm(pool);gc(FALSE)`; keepalive still holds within a chunk so throughput is unchanged. VERIFIED: full shard (5,998 urls) completes in 2.6 min, sails past 3000.
- The collector's "missing"/retry urls are NOT a defect - probed 40, **38 are HTTP-403 bot-blocks** (need the headless-Chrome residual lane; even a synchronous Chrome-UA GET 403s), ~5% transient. So leave the collector fetch settings alone.
- Full-coverage run = `CU_PIPE_FETCH_RESIDUAL=1 Rscript run_cu_pipeline.R` (fast collector + the now anti-stall-bounded chromote residual lane + scoring); plain `Rscript run_cu_pipeline.R` skips the 403/JS residual for max speed. `FULLTEXT_MODE` stays "all" - correct here, it only governs which cached rows get SCORED (SKIP_FETCH means no fetching). (Later the same day the recommended run became plain `Rscript run_cu_pipeline.R` and `CU_PIPE_FETCH_RESIDUAL=1` became redundant: see next section.)

### Chromote 403 lane + THREE coverage bugs fixed (2026-06-19)
Added a headless-Chrome pass to each collector worker (after curl main+retry) for HTTP-403 bot-blocked URLs - own Chrome per worker, `setTimeLimit(JS_NAV_TIMEOUT)` bound, same `extract_release`+`flush_ck`, writes same checkpoints, skip via `CU_TC_NO_CHROMOTE=1`. Then a coverage audit of the completed 45-min run (`coverage_audit.R`, kept as reusable verifier) found coverage was only **254,477/293,935 = 86.6%** with **3 bugs**:
1. **ORCHESTRATOR ABANDONED HEALTHY WORKERS at 10min** - the stall guard read worker *stdout logs*, but `message()` -> system2-redirected file is **block-buffered on Windows**, so the orchestrator saw an empty/stale log, counted "no progress," and killed all 6 workers at exactly 20 polls x 30s - mid-chromote (logs cut off at 16-33% of the 403 backlog, ~14.5k recoverable 403s thrown away, all `fail 0`).
2. **THROTTLE-VICTIMS DROPPED** - the hot main pass (40 conn) makes gov WAFs (senate.gov/house.gov, esp. Cantwell C000127 6,106 urls @ 0% bodies) drop connections (transport-`fail` -> retry) or serve body-less 200 challenge pages (2xx-no-body -> `miss`); the single same-concurrency retry recovered few and the rest were **silently discarded** (probe: 22/24 still-missing return a FULL static body via serial curl; ~28.8k of the 39.5k gap).
3. 403s -> chromote already worked, just abandoned by bug 1.
**FIXES in `cu_text_collector.R`:** (A) orchestrator now reads reliable `.hb` sentinels (cumulative `acc$n_ok` via `writeLines` open/write/close = flushed each step) + `.done` sentinels, not buffered logs; idle-guard 20min on *body* progress + `CU_TC_CAP_MIN=300` absolute cap. (B) `collect()` captures 2xx-no-body to `acc$miss`; after main, a **GENTLE RECOVERY loop** (<=3 passes, `total_con=8 host_con=2 robust=TRUE` w/ `forbid_reuse`, 5s cool-down between) drains retry+miss and re-fetches - hosts cool down so it recovers progressively; leftovers route to chromote (`on_block`). `run_all` gained `total_con/host_con/robust` params; `mk_handle` gained `robust`. VERIFIED smoke (300-url worst-case shard): main 160 ok -> recover 185 -> 209 -> **233** (+73, +46% that the old code DROPPED). Projected full coverage ~**97-98%** (~32.7k recoverable: 28.8k throttle + 3.9k 403; ~5.1k genuine 404 dead).
**Recommended run now = plain `Rscript run_cu_pipeline.R`** (collector does curl+gentle+chromote itself; step-2 residual no longer needed; the many-to-many join warning is benign - 0 dup member URLs, it is committee/third-party attaching one url to multiple members; but see the 2026-06-20 `stage_score` dedup fix in [[2026-06-feature-congress-r-scrapers-press-discovery-and-attribution-fixes]]). Do not run with `CU_PIPE_FETCH_RESIDUAL=1` anymore (redundant double chromote). **Default `CU_TC_PROCS` raised 6 -> 8 (2026-06-19, user request - box has GPU/RAM headroom for 8 R workers + 8 headless Chrome).** Each worker now drives its OWN Chrome in the 403/chromote pass, so 8 shards = up to 8 Chrome instances (GPU-accelerated render); lower `CU_TC_PROCS` if RAM/GPU tight.

### `CU_PR_NO_CHROMOTE` leak silently killed collector chromote (2026-06-19)
The 8-shard run finished 37.6min but scored count stayed flat (272,252 ~ prior 272,638; CU-relevant 3,821 vs 3,806) - because **every shard skipped its chromote pass** (`blk=0(recovered 0)`, ~3min/shard; ~15.4k blocked-403 URLs across 8 shards left unfetched, coverage stuck ~87% not the intended ~98%). Root cause: the collector's 403 chromote pass gated on the scraper's `HAVE_CHROMOTE`, which is `requireNamespace(chromote) && !nzchar(CU_PR_NO_CHROMOTE)` - and `CU_PR_NO_CHROMOTE=1` (the scraper's STEP-2 score-from-cache switch, set by `run_cu_pipeline.R`) had **leaked into the collector worker env** (transient shell export; NOT persistent - User/Machine env confirmed empty). It disabled chromote at TWO points: the gate AND `js_session()`'s own internal `if(!HAVE_CHROMOTE) return(NULL)` (so even forcing the gate, every Chrome fetch insta-failed `0.0 s/url fail`).
FIX (the collector owns chromote, must be immune to that scraper flag): (1) at top of `cu_text_collector.R`, before sourcing: `if(!nzchar(Sys.getenv("CU_TC_NO_CHROMOTE"))) Sys.unsetenv("CU_PR_NO_CHROMOTE")` -> HAVE_CHROMOTE/js_session come up enabled; (2) new `TC_CHROMOTE <- requireNamespace(chromote) && !nzchar(CU_TC_NO_CHROMOTE)` gates the collector chromote block (decoupled from the scraper flag); (3) always-on log line `[shard N] chromote gate: enabled=… | M blocked(403) urls queued` so it can never be silently off again. VERIFIED with the leak simulated (`CU_PR_NO_CHROMOTE=1`): before fix gate-enter but `recovered 0/126 (0.0s fail)`; after fix `enabled=TRUE`, chromote launches, **recovered 74/74 fail 0**. The collector's curl/gentle-recovery worked (ok climbed across recover1-3) but under 8-worker load most throttle-victims fell through to chromote (genuine 403s + WAF-throttled), so chromote being off = the gap. Re-run now hits ~97-98%; chromote tail = blocked-403 pages load ~1-3s each in Chrome -> ~30-100min across 8 workers (resumable). Lesson: a shared ambient env var (`CU_PR_NO_CHROMOTE`) controlling two components is fragile - give each component its own switch.

### Validity verdict + signal-prioritized collection (2026-06-19)
Before grinding the last ~13% coverage, MEASURED whether the missing data invalidates the CU results (a missing-data/bias question, not a coverage-% one). Method: apply the relevance detector to index TITLES (titles exist for un-fetched pages) and calibrate vs actual scored outcomes. Calibration: P(CU-relevant | CU-term title)=0.825 vs P(relevant | generic title)=0.0089 (titles ~93x discriminating). Result: captured 2,410 member-press CU-relevant; **imputed missing ~265 (~10%)** - but only ~9-138 are title-identifiable, the rest are incidental body-only mentions (~0.9% rate across 28.7k pages).
**VERDICT: missing data does NOT invalidate.** (1) Party-balanced: missing CU-signal 9.6% (D) vs 10.2% (R) - the raw coverage gap (D 92.5% vs R 87%) is entirely CU-IRRELEVANT bulk; (2) missing-at-random by content (WAF blocks by host/rate, cannot read content -> each member's captured releases are a random sample -> unbiased scores, just slightly noisier; Senate noisier than House, 83% vs 96%); (3) of 29 members <50% press coverage, **28 are rescued by the independent cosponsor/ACU/committee layers** - only 1 truly uncovered (Alan Armstrong, a near-zero-press newcomer, nothing to recover). Press is 1 of 4 layers; cosponsor/ACU/committee (1,300+ signals) are 100% complete. So results are valid as-is; a 2-3h full grind would recover only weak party-balanced MAR noise.
**ADJUSTMENT - `CU_TC_CAP` signal-prioritized stratified collection (default 1000, in the `cu_text_collector` orchestrator):** ALWAYS fetch every page whose TITLE matches the scraper's `TOPIC_CORE_RX` (credit-union/NCUA/interchange/CFPB/Durbin/CDFI + all tracked bill names - in scope after sourcing; 138 uncached such pages = the recoverable signal) + up to CAP most-recent GENERIC-titled pages/member (unbiased recency bulk sample for body-only mentions/coverage). Skips heavy members' deep CU-irrelevant archives (rate-limited ~2s/page). `read_index` now also carries title; `CU_TC_CAP=0` = full fetch. Sizes: CAP=500 -> 8.1k (~34m), 1000 -> 14.0k (~30-58m), 1500 -> 16.9k. Statistically equivalent to full fetch at a fraction of cost; also evens shards (no member's bulk > CAP -> no multi-hour pole).
**Chromote stability+speed fix:** replaced `setTimeLimit` (async interrupt corrupted chromote's websocket -> "Operation was interrupted"/"Execution halted" crashes) with a self-managed session bounded by chromote's OWN `default_timeout` (`.tc_js`/`tc_js_new`/`tc_js_fetch`; a timed-out CDP call throws a normal catchable error -> recycle session, skip url) + trimmed settle (0.3+0.3). VERIFIED: 117/117 recovered, fail 0, **0.5 s/url** (down from 2-4), no crash, exit 0. Reusable verifier: `coverage_audit.R`.
