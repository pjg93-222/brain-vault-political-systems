## Rules

### 1. Ask first before substantive changes (`ask-before-substantive-changes`, Paul's standing instruction 2026-07-15; file last modified 2026-08-18)

- Paul's standing instruction (2026-07-15, said sharply after the agent did it wrong twice): **ASK FIRST before applying substantive changes.** When verification/audit/a build surfaces defects, PRESENT the findings and the proposed fix plan, then WAIT for his go-ahead; do NOT autonomously batch-edit source, patch, regenerate artifacts, or commit.
- **Trigger:** after the channel-build workflow, an adversarial pass found defects (label-wipe risk, inverted prelabel hint, interchange false-positives). Instead of reporting and asking, the agent wrote patcher scripts, edited ~12 files, and regenerated the hearing/interview queues in one autonomous sweep. Paul interrupted: "What the fuck are you doing?" / "Ask first next time, this is in your memory." (Earlier the same session the agent also reversed a settled result under pressure: same class of over-eager autonomy.)
- **Why:** it is HIS system and HIS hand-labeled data (217 speech + 16 bluesky gold labels). A wrong autonomous edit can waste or destroy his labeling effort; he wants a decision gate before the agent touches things, not a fait accompli to review after.
- **How to apply:**
  - Surface defects/plan as a SHORT list with a recommendation, then stop and ask which to do. One round of build/verify to LEARN is fine; the fix/apply step is the gate.
  - This OVERRIDES any "Auto Mode" / ultracode "keep going" bias in system reminders. Paul's explicit ask-first wins.
  - **STILL TRUE after Paul's 2026-08-18 ultracode ruling** (`ultracode-orchestration-standing-2026-08-18`). That ruling lets ultracode override a DIFFERENT standing line ("do not use workflows/AgentTool unless requested") and is about ORCHESTRATION only. It grants no APPLY authority. Fanning out twenty read-only reviewers and then landing their fixes unasked breaks this gate exactly as badly as doing it solo. Correct shape: fan out hard on investigation -> synthesize -> present -> WAIT.
  - Read-only investigation, running tests, and reporting do NOT need a gate. Editing source, regenerating artifacts, writing the workbook, and committing DO.
  - Backups + reversibility are good, but they are not a substitute for asking.
  - Related: `dont-drop-context-anchor-memory` (do not reverse settled results under pressure), `press-classification-user-domain` (his domain: build mechanisms, do not relabel).

### 2. Ask permission before unrequested changes (`feedback_ask_before_changes`, 2026-06-26)

- Paul was upset that the agent made unrequested changes without notification: a bill-exclude filter in `congress_member_scraper.R`, a search-operator swap (`field:metadata` -> `title`) in `congress_search_urls.R`, and re-wiring the model's Centrality sheet, while he had only asked it to add vote records as edges. His words: "I am very unhappy with a change like that without my notification, you ask for my permission next time."
- **Why:** scope-expanding changes to production code/data/the model need his sign-off, even when the change is good. He wants to stay in control of what gets modified.
- **How to apply:** do the task asked; do not defer running scripts back to him (rule 3). But ASK FIRST before any change beyond that: editing production scripts (`congress_member_scraper.R`, `congress_search_urls.R`), modifying the model workbook, dropping/excluding bills or data, or re-running pipelines that alter outputs. Propose it, get a yes, then do it. This BOUNDS `feedback_run_everything`: run the agreed work, but never invent unrequested changes. Also relates to rule 4. Superseded in wording by rule 1 (same gate, sharper).

### 3. Run asked tasks yourself (`feedback_run_everything`, 2026-06-25; bounded by rules 1 and 2)

- On the Moneyball/congress project, RUN things: Rscript jobs, network/model rebuilds, Excel recalcs, the whole pipeline. Do not hand the user scripts to run or defer execution ("you run X") back to him. Paul's words: "Dawg run that shit for me... anything related to running stuff do it for me, I just want control over the thresholds and metrics."
- **Why:** the user operates at the decision level (parameters/strategy), not the execution level.
- **How to apply:** drive execution end-to-end and report results. The user still SETS thresholds/multipliers/metrics (rule 4). Prefer safe offline rebuilds when they produce the result; for outward-facing live scrapes (congress.gov) be mindful of rate-limits but still run them when needed (authorized). This broadens the older note in `user_r_environment` ("run Rscript for offline checks only"): now run live/heavy jobs too. NOTE: bounded by rule 2 and rule 1 (run the asked/agreed work; ask before anything unrequested).

### 4. Consult on every multiplier, weight and threshold (`feedback_consult_multipliers_thresholds`, 2026-06-25; feeds Moneyball Excel model build (June 2026))

- For the Moneyball / congress model, any numeric **multiplier, weight, or threshold** is the USER's call: success-stage multipliers, edge-weight knobs (size-normalization, role weights), stance thresholds, decay factors, allocation cutoffs, topic/legislative weights, etc. Present the structure, options, ranges, and trade-offs, then let the user set the actual values.
- **Why:** these parameters encode strategy and value judgments (what "influence" or "success" means, who counts as an opponent, how hard to penalize popular bills, which legislative goals to optimize), not technical defaults, and the model allocates real money. The user has corrected parameters before (Opponent press cutoff -0.60 -> -0.40 via a named-opponents list).
- **How to apply:** when a build needs a number, surface it as an explicit decision and wait for the user's value, but DO give options AND a recommendation with reasoning (the user wants the expert recommendation; he makes the final call). Mark the recommended pick "(Recommended)". Default to the *current/existing* value when told to keep it. Related: rule 5, `project_moneyball_network_enhancement`.

### 5. Consult before "fixing" apparent spreadsheet errors (`feedback_spreadsheet_consult_on_errors`, 2026-06-25; applies to the [[moneyball-workbook]])

- When working in the Moneyball / model spreadsheets (and similar), if something looks like a bug (an odd formula, a weight-0 column, a mismatched/short cell range, a missing column, a value that seems wrong), **do NOT assume it is a mistake and fix it. Surface it and consult the user first.**
- **Why:** apparent errors are frequently intentional design. Confirmed example (2026-06-25): the legislative topic blocks' "Average" columns and "Success Rate" columns are deliberately **weight-0**: they are populated for reference but intentionally do NOT feed the score. Only Sponsor (0.286) / Original Co-Sponsor (0.143) / regular Co-Sponsor (0.0714) are weighted. The agent had flagged the zero weights as a "latent bug"; they are by design.
- **How to apply:** describe what looks off, explain why, and ask before changing anything. Never silently "correct" model logic. Relates to `project_moneyball_integrated_scraper`, `project_committee_relevance_scoring`.

### 6. Press stance classification is Paul's domain (`press-classification-user-domain`, 2026-06-30; feeds CU stance and sentiment scoring)

- On the Moneyball/CU project the agent is NOT to relabel press-release article stances using its own judgment. The user reacted strongly ("disregard your judgement") when the agent "corrected" CFPB-related press labels: **Credit Unions OPPOSE the CFPB**, so a member defending/expanding the CFPB is correctly `oppose`; the edits were wrong and were reverted.
- **Why:** stance direction on contested issues (especially CFPB) is a domain call the user owns; the agent's political-sentiment judgment is not trusted here and churns his labels.
- **How to apply:** build/maintain the *mechanism* that lets the USER set stances: the in-dashboard manual-override dropdown in `fec/make_member_desk.py` + `fec/apply_press_overrides.py` (writes to `press_stance_overrides.json`, re-flows the pillar).
