## DE-026 — `subprocess.run(capture_output=True, timeout=N)` as a bounded call
Date: 2026-09-18
Approach: Treating `subprocess.run`'s `timeout` as a guarantee that the call returns, and `@lru_cache` as a single-flight guard for an expensive lookup. The shape that shipped was `git_sha_cached()`: an `@lru_cache` wrapper around `subprocess.run(['git','rev-parse','--short','HEAD'], capture_output=True, timeout=10)`, called on the request thread.
Failure mode: `run()` answers a timeout by re-entering `communicate()` to drain, and `communicate()` blocks forever joining the pipe-reader threads of a child that still holds the inherited handle. Measured 10.11 s for a 1 s timeout against a child that leaked stdout to a grandchild, and unbounded against a `git.exe` wedged on OneDrive placeholder I/O - two orphaned children alive and unkillable for about an hour on 2026-09-17, with the page's fetch pending the whole time. Separately, `@lru_cache` ran eight lookups for eight concurrent callers, so a single page load raced two request threads into the same lookup.
Root cause: the timeout bounds the wait, not the drain; and `lru_cache` memoizes a result, it does not serialise entry.
Would reconsider if: CPython bounds `run()`'s drain on the timeout path. Until then use `Popen` with stdout to a real file handle, `wait(timeout)`, `kill()`, and an explicit lock for single-flight - `mentat/app/server.py:279` and `:336` are the worked example, and the new plumbing waits 1.03 s for a 1 s timeout where the old waited 10.11 s.
