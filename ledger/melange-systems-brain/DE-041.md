## DE-041 — Cutting a patch against LIVE bytes by string replacement or 
Date: 2026-09-19
Approach: Cutting a patch against LIVE bytes by string replacement or str.splitlines, trusting an EOL-normalised hash as the drift check, and applying it with a plain `git apply`
Failure mode: MEASURED 2026-09-19 (git 2.54.0.windows.1; scratchpad eol_lab results.json and results_e9.json; reproduced on LIVE fec/stance/build_media_blend.py lines 18/19). (1) A two-line anchor joined with CRLF returns -1 where the first line ends in a bare LF, while the CRLF-normalised sha256 equals the pure-CRLF copy's: the failure is silent and the drift check says identical. LIVE fec/audit/dashboard_integrity.py had 88 such lines in 11 runs, not the one first reported. (2) str.splitlines(keepends=True) split an 8-line file into 10 at a raw form feed and a U+2028 and `git apply --check` rejected the patch; splitting on LF only was byte-exact (0 of 2,228 tracked text files held those separators that day, so this was latent). (3) A patch cut against mixed bytes fails against the normalised file and against the index (--cached); --whitespace=fix does not rescue it; --ignore-whitespace applies it but injects the patch's own terminators. (4) Under core.autocrlf=true, a file-patch whose old lines are ALL bare LF matches CRLF targets by renormalisation and a plain `git apply` rewrites the WHOLE file as CRLF with rc 0 (201 lines of a copy of fec/lobbying/lobby_posture.py); --check gives no warning and `git diff --stat` shows one insertion; a single CRLF old line anywhere in that file's patch suppresses it. Applying outside a repository does not avoid it on this box. [[ledger/melange-systems-brain/DE-040|DE-040]]'s 'in-repo apply stopped matching LF-only hunks while the same bytes applied outside a repo' was NOT reproduced: in-repo they matched in every autocrlf=true case, and outside-repo application was not byte-exact either.
Root cause: The working tree's terminators are whatever the last writer used (git checkout writes CRLF, the Write tool and most scripts write LF, in-place cutters inherit their payload's); git never rewrites a file it considers unchanged; and `git apply` chooses between a renormalising and a literal read per file-patch from the patch's own old lines, with core.autocrlf=true coming from the SYSTEM gitconfig and so in force even outside a repository.
Would reconsider if: Never. Cut with fec/tools/live_patch.py ([[ledger/melange-systems-brain/D-060|D-060]]), prove with prove(), apply with `git -c core.autocrlf=false apply` or apply_to(), and keep cut patches outside the repo or under a -text attribute.
