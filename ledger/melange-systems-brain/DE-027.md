## DE-027 — `git update-index --force-remove` as a rollback for a staged path
Date: 2026-09-18
Approach: Unwinding a partly-staged commit in the shared-index Mentat worktree by running `git update-index --force-remove <path>` on each path already staged, to put the index back the way it was.
Failure mode: `--force-remove` does not unstage a path, it deletes the index entry, so `git diff --cached` then reports the file as DELETED against HEAD - a worse state than the one being undone, and one that would have committed a deletion had it not been caught. The staging run that needed rolling back had itself been aborted mid-flight by a second trap found the same day: piping a native command into `Select-Object -First 1` terminates the upstream pipeline and poisons `$LASTEXITCODE`, so the script's next success check read a successful git call as a failure and bailed with one path already staged.
Root cause: `--force-remove` is how you record a deletion in the index, the write half of `git rm --cached`; nothing in it consults HEAD, so it cannot restore anything. The undo primitives that do consult HEAD (`git reset -- <path>`, `git restore --staged`) were off the table because four sessions share this worktree's index and a `git reset` there had already cleared a peer lane's staged list, so the rollback had to be per-path and explicit. The PowerShell half is pipeline short-circuiting: `Select-Object -First 1` stops the upstream command, and a terminated native command leaves `$LASTEXITCODE` unrelated to whether the command did its job.
Would reconsider if: never for rollback. Capture the path's HEAD blob and mode FIRST (`git rev-parse HEAD:<path>` and the mode from `git ls-tree HEAD -- <path>`) and restore with `git update-index --cacheinfo <mode>,<HEAD sha>,<path>`; and never let a native command's exit status reach a check through `Select-Object -First 1` - assign the full output, test `$LASTEXITCODE`, then slice.
