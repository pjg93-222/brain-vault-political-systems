## D-014 — hash_always covers only what git does not protect (the narrow scope)
Date: 2026-08-27
Status: ACTIVE
Decision: In the system manifest, `hash_always` applies ONLY to material git does not already protect. A store git tracks is refused `hash_always` and downgraded, and the refusal is RECORDED rather than silently applied. Tracked-ness is MEASURED (one cached `git ls-files -z` per root), never taken from a declared field.
Context: Paul ruled "use the narrower scope" during containerization Phase 0. Encoded as a SECOND refusal ordered AFTER the scale envelope, so a store too big to hash still reports `scale` and keeps its sentinel evidence. Effect: 16 -> 8 `hash_always` stores, 280 -> 8 files, 2.79 MiB.
Rationale: Hashing what git already content-addresses buys nothing and costs a re-hash every gate run. The ruling's PREDICTION HELD, which is the evidence it was right: three A2b/A4 failures that fired when a concurrent lane wrote into `fec/audit` and `fec/tests` became structurally impossible, because those stores now carry neither hashes nor sentinels. Four tracked stores DECLARE `hash_always` and are refused every run deliberately -- the refusal is the standing record that git stands behind them.
Measurement status: the POST-ruling figures verify exactly against both committed manifests (8 stores / 8 files / 2.79 MiB, unchanged across the later sentinel fix; the manifest carries the ruling itself at `policy.hash_always_scope.ruling`). The PRE-ruling figures "16" and "280" are UNVERIFIABLE -- they describe a counterfactual manifest that was never committed, and the committed artifact records `integrity_policy_declared: hash_always` on 13 stores, not 16. Do not re-quote 16/280 as measured.
Note on an internal inconsistency now resolved: the brain recorded "four tracked stores refused" in one line and "5 policy refusals" in another. FIVE stores are refused -- four to `hash_never` (repo.bill_beneficiary_tags, repo.industry_axes, repo.acu_outline_docx, glassbox.scripts) and `repo.audits` to `sentinel_files` on scale. "Four" is the `hash_never` subset.
Reversal condition: A store is shown to need byte-level verification git demonstrably does not provide for it -- a tracked file whose working-tree form diverges from its blob by design. CRLF is NOT such a case (see the autocrlf constraint). Widening the scope back requires Paul.
