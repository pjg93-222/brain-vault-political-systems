## DE-010 - A file_count tolerance band over a git store
Date: 2026-08-27
Approach: Asserting that a git store's file count stays within a per-size-class tolerance band, the
same way every other store in the system manifest is checked (A2 scale).
Failure mode: FALSE POSITIVE BY CONSTRUCTION. A git store exists in order to change: a commit writes
loose objects, a push writes more, `git gc` deletes thousands at once. Fired live on the Phase-0
landing commit - `mirror.melange` went 86 -> 100 files (+14 objects that push added) against a
+/-5 SNAPSHOT tolerance, and the audit called it a disagreement.
Root cause: The EXPECTATION was wrong, not the check. Count stability is not a property a git
directory has, so pinning one asserts an invariant the store does not hold.
Replacement (shipped, in the same check slot so the section still emits 333 checks): assert what a
mirror CAN honestly promise and an emptied one cannot -- that it still holds a populated git object
store (`_git_object_store_populated`). Existence (A1), coarse size_class (A2) and the
content-addressed sentinels (A2b) are unchanged.
KNOWN GAP in the replacement, measured 2026-08-27 and NOT yet closed: because A2 no longer asserts
file_count for a git store, a large collapse in that store's file count is invisible to A2. Worked
example - `.git/lost-found` is 17,174 files = 95.57% of repo.git's file_count; deleting it would be
caught ONLY by A2b, and only because one lost-found blob happens to occupy a sentinel slot.
Would reconsider if: never as a tolerance band. A replacement that bounds count MOVEMENT rather than
count VALUE (objects may be added freely, but a >50% drop between runs is reported) is a different
approach and is NOT covered by this dead end.
