## DE-011 - Newest-file sentinel selection inside a git directory
Date: 2026-08-27
Approach: Recording each store's newest file as a sentinel with `content_stable: true` and a pinned
sha256, applied uniformly including to git directories.
Failure mode: THE ALWAYS-RED TWIN OF NEVER-FAILS. Inside a git directory the newest file is by
construction whatever the last commit or push just wrote, so the sentinel is falsified by ordinary
operation. It fired on the gate's OWN landing commit: `.git/index` 8,371,954 -> 8,372,431 bytes, and
`mirror.melange`'s `refs/heads/main` recorded the sha256 of the PRE-PUSH ref, so the audit's
"disagreement" WAS the push.
Root cause: A sentinel is an expectation re-checked days later, so anything ordinary operation
rewrites is disqualified from sentinel DUTY. Git bookkeeping - index, refs, reflogs, packed-refs,
transient *_HEAD pointers, in-flight rebase/bisect state, regenerated caches - is exactly that.
Fixed at the root rather than by regenerating the manifest, which would only have deferred it one
commit. Git OBJECTS stay eligible on purpose: a loose object or pack is named by the hash of its own
contents, so it cannot change without changing its name.
Would reconsider if: never - git bookkeeping changes by design. Residual the fix does NOT cover:
`repo.fec_code` and `repo.audits` still take newest-file sentinels, so a commit touching one of those
RECORDED paths still falsifies A2b. Narrower (it fails only if that specific file moves, not on every
commit) but the same family; extending the rule to them is Paul's call and is still OPEN.
