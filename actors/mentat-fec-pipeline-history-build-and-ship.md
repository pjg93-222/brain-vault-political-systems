### Parallelism ceiling + worker-shard audit (2026-07-21, 16 keys added)

- ~~THE structural finding: `api_request_budget` is tracked PER-DATABASE, not per-key: one row (`budget_id='openfec'`), NO key column.~~ **PARTIALLY CORRECTED 2026-07-22: "no key column" was FALSE.** The schema is `api_request_budget(budget_id TEXT PRIMARY KEY, window_started_epoch, requests_used)` and is byte-identical in all four lineages: it always supported multiple budget rows. What was true is that the CODE hardcoded `budget_id='openfec'`, collapsing every worker onto one 1,000/hr bucket. A LATER fix in `mall`/`Mentat\mentat` only (`fec_api_budget_id()`, a polynomial digest of the key) makes the budget genuinely per-key. **Its premise (that api.data.gov enforces the hourly cap per registered KEY) is UNVERIFIED and contradicts the original conclusion. Do not propagate that fix or promise throughput gains from more keys until an empirical two-key test settles per-key vs per-IP/per-database.** Paul QUARANTINED it 2026-07-22: present where it already is, added nowhere. Verify budget rows before promising any throughput gain.
- Built unit-level fan-out (`gapfill_worker.R` + `mentat_scheduler2.py`, branch `codex/unit-shard` in `C:\Users\pgoff\cxwt2`): shards a company's pending unit list across keys, each worker its own DB + own budget, writeback marks parent units complete on exit.
- **4-agent adversarial audit of the collector (all claims source-verified):** (1) `stored_complete=1` DOES skip work, at TWO points: fetch queue `fec_api.R:747` (via `complete` at :630) and store phase `:1688`; resume-skip was NEVER removed (diff vs `fec_api.R.bak` = only 2 unrelated stop -> warning hunks). (2) **`api_work_progress` is purely a FILTER**: intersected with incoming units at `:589`, it can never ADD work. **P2_name units are minted from `contributions.sub_id` (`:1137`) seeded from `phase IN ('P1_employer','P2_variant') AND company_match_status='accepted'`.** A worker DB seeded with checkpoints but NO contributions generates ZERO units, returns the `:719` zero-result, and **silently collects nothing while logging a clean START/END** (0 of 237 units, 0 rows). (3) LATENT SILENT-LOSS: `api_page_checkpoints` was never seeded: a unit restored `fetched_complete=1/stored_complete=0` gets `pages=list()`, is marked `complete` at :630, PASSES the `:1690` guard, stores nothing, then is marked stored at `:1705`. Never fired (fan-out disabled before any assigned unit completed).
- FIX BUILT + VERIFIED, **NOT DEPLOYED** (commit 7b2e0eb): seed phase-1 contributions + page checkpoints, force assigned units `stored_complete=0` (they were inheriting the parent's 1 via `completion_clause=""`). Proven: seeded 24,299 rows == parent's 24,299 Allstate P1/P2v accepted.
- **UNRESOLVED, TWO DISTINCT WORKER FAILURES (do not conflate):** (i) under ~5-way concurrency, `gapfill_worker.R` dies with ACCESS_VIOLATION `rc=3221225477` 10/10, no R error text; (ii) run STANDALONE it survives 28 min then exits 0 having logged `FAIL attempt to apply non-function`, an R-level error inside `collect_crypto_api`, NOT a memory fault, after burning its **entire 995-request budget while storing ZERO rows** (units 6/1577, rows flat at 29,895). Ruled out: no global name collision between the worker's helpers (parse_phase2/quoted_identifiers/copy_rows/chunks/seed_worker/main) and any assignment in `collect.R`/`fec_api.R`/`ingest.R`/`schema.R`. Likely lead: the worker DB is in a state no plain lane reaches: `run_ca_w01` contributions are **100% `P2_variant`, 0 `P1_employer`** (old seeding copied `stored_complete=1` progress rows, so phase 1 was skipped as done, while copying no contributions). The 7b2e0eb seeding fix targets exactly that state but is NOT proven to fix this error: reproduce with an R traceback (`options(error=...)` / tryCatch capturing `sys.calls()`; plain `try()` discards it) before believing it. The worker also wastes budget fastest: a full key-hour for nothing. Do not re-enable fan-out until (i) and (ii) are both understood. Dials: `MENTAT_UNIT_SHARD_MIN` (huge = unit shards off), `MENTAT_NO_WORKERS=1` (plain lanes only, the proven-stable path: plain `gapfill.R` has never crashed).
- **OPS LAWS learned the hard way (07-21 night):** (a) never build stall/progress detection on `rows_seen`: it is a FETCH-side counter that churns when a lane re-fetches and fails to store, so a failing lane relaunches FOREVER (ca relaunched 10x, never retiring, re-pulling ~6k rows from FEC each time); use COMMITTED `contributions` count. (b) The scheduler polls every 120 s, so many "lane exit" lines sharing one timestamp is polling granularity, NOT simultaneous death: do not infer an external killer. (c) R writes via **WAL**: committed-row queries look frozen while `mentat.db-wal` grows; check `-wal` mtime/size before declaring a stall. (d) **FEC bulk data is UPPERCASE**: a case-sensitive prefilter returns a FALSE ZERO (a Caterpillar scan reported 0 rows when 785 existed in the first 3M lines alone; the implausible answer is what caught it). (e) Long unit-id lists overrun the Windows 32K argv limit -> every worker dies instantly with `command line too long`; pass a `@<path>` filter FILE. (f) Launch detached schedulers with stderr REDIRECTED (a hidden crash, a `c.units` typo where the field is `pending_units`, killed the scheduler on first lane exit for an hour, invisibly).
- **BOTH PHASE-2 ROOT CAUSES FOUND + FIXED 2026-07-21 evening (`fec_api.R`, backup `.pre_storefix`):** (1) **store-unreachable:** fetch -> record -> store in `fec_api_collect_checkpointed`, and ANY abort during fetch (quota pause OR plain error like connection_error-after-5-retries) unwound past the store call: fetched pages stayed in `api_page_checkpoints` forever. Fix: tryCatch `error =` handler flushes all fetched-complete-unstored units via `fec_api_store_results` (states from `fec_api_load_progress` need `state$unit` attached: load_progress alone lacks it) then re-stops the original condition. (2) **the `identity` shadow:** `collect_crypto_api` line ~2079 rebinds `identity` to the phase-result LIST; `collect_phase`'s tryCatch handlers (`mentat_api_quota_exhausted = identity` etc.) resolve `identity` in that SAME env at call time, so every pause after the rebind called a LIST -> "attempt to apply non-function" at the exact moment a key's 1000 budget ran dry (error always near 997/1000 used, only phase2 runs, plain AND worker lanes). Fix: all 7 handler sites -> `function(condition) condition` (shadow-immune). **PROOF on cu: identity units 0 -> 2,633/2,656 stored, fetched_unstored 2,573 -> 0, +1,813 P2_name rows (52,280 total).** Identity pass yields ~few % net-new rows (mostly INSERT OR IGNORE dupes of the employer pass): its value is unit completion, not volume.
