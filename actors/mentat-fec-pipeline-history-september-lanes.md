### Worker-scaling lane (2026-09-09, on Paul's "finish the job / get it done" gate)

Mentat collection (`C:\Users\pgoff\Mentat`, the R+Python FEC console, separate from the Moneyball worktree) was running a single worker and ignoring stored keys.
- **Root cause, from the live manifest of the 09:47 banking run** (`%LOCALAPPDATA%\Mentat\console\<id>\runs\...\industries\banking\fanout\manifest.json`): `key_cap 1`, `memory_lane_cap 2`, `company_cap 10`, `sqlite_merge_cap 10` -> `active_lane_cap 1`. Only ONE key reached the fanout. `active_lane_cap = min(requested, key_count, company_count, memory_cap, 10)`: any factor at 1 pins the whole run to one lane.
- **Four limiters, in the order they bite:** (1) **Keys:** `discover_keys()` reads `FEC_API_KEYS`/`FEC_API_KEY_N`/DPAPI store; the console joins `stored_keys` with `|`; one key = one lane, always. (3) **SQLite ATTACH:** was a hard 10 (real limit `too many attached databases - max 10`, confirmed by execution). (4) **Companies:** more lanes than companies is pointless.
- **Shipped (all UNCOMMITTED in the live Mentat tree at the time, `.bak-20260909` beside each file):** `merge_company_shards.py` (>10 shards merge into a staged copy in batches, atomic replace only after every batch commits; <=10 keeps the old path byte-for-byte; proven: 12-shard batched vs serial reference identical on all 12 tables; a mid-merge shard corruption left the target byte-identical, same sha256, no staging leftovers); `api_company_cycle_fanout.py` (10 dropped from the min(); `--merge-batch-limit`, `--max-lane-ceiling`; a failed memory probe no longer silently collapses to 1 lane, emits `memory_probe_failed`; `LaneLimiter` resizable condition-variable gate replaces BoundedSemaphore; polls `<run_directory>/control.json` every 3 s; publishes `workers.json`; exit code **3** = stopped by operator, distinct from 2 = failed); `server.py` + `index.html` + `app.js` (`POST /api/stop` graceful, Shift-click sends `force:true` -> `taskkill /PID /T /F`; `POST /api/workers` 1-64; Stop button + worker box); `fec_key_store.py` (`key_id()`, `inventory()`, `set_disabled()`, `--list/--enable/--enable-all/--disable` so disabled keys can be recycled; nothing in production ever called the disable path, so no key was quarantined: store had 15 active, 0 disabled); imported the 7 `data_gov` keys from `Desktop\API Keys\keys.json`; store now holds **22**.
- **Second pass, same day, after Paul reported "it doesn't stop" and "can't change the number of bots":** lanes were planned at the RAM-derived cap so the limiter could only throttle DOWN. Now `lane_count = max(1, min(len(keys), len(companies)))` and RAM only sets the STARTING count via `--initial-workers`. The PS orchestrator passes `MaxParallel = $MaxParallel` (operator's value, 0 = auto) and `InitialWorkers = $liveFanoutPlan.effective_api_lanes`. Slider range 1..lane_count, live.
- **`Future.cancel()` was a no-op and the graceful stop did nothing:** `ThreadPoolExecutor(max_workers=lane_count)` with exactly `lane_count` futures submitted means every future is RUNNING within milliseconds, and `cancel()` only works on PENDING. - **A running collection started before these changes has no control channel and cannot be steered: it must be killed and restarted.** Console restart is also required to pick up the new `server.py`.
- **Safety property worth keeping:** a stopped run can never write the source database. Stop cancels queued lanes -> tasks unfinished -> `final_failed` non-empty -> the `if not final_failed:` guard skips the merge entirely. Resume with `--resume` later.
